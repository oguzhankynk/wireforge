# Fitting WireForge into a DO-178C process

WireForge's code, tests and documents fit into your DO-178C process as they are. Your high-level requirements stay in
your own requirements tool. WireForge produces the low-level requirements that refine them, the code, the tests and the
results in the formats your tools read (ReqIF, CSV, JUnit, Cobertura) and with your id scheme. Every baseline comes
with a traceability matrix and a mapping to the DAL C objectives. Nothing is locked in: it is all plain text in git.

Generated code still goes through your verification process: WireForge automates that verification and its evidence; it
does not remove it.
The generator is not a qualified tool.
No document says that a result is certified or compliant. The documents are evidence for, and support, the objectives
of your process (docs/LIFECYCLE.md).

## Who does what
| | WireForge | You (the applicant) |
|---|---|---|
| High-level requirements | imports a snapshot of a baseline; never edits them | write and baseline them in your tool |
| Low-level requirements | derives them from the model, numbers them, exports them | review them, bring them into your tool |
| Code and tests | generates them with the requirement ids in comments and test properties | review, build and run them on the target |
| Results and coverage | reads JUnit and coverage of a run and reports gaps | run the tests, justify the gaps |
| Traceability matrix | derives it; never maintained by hand | scan it in your tool if you want it there |
| DAL C objectives | maps documents to objectives, marks the ones that are yours | planning, quality assurance, certification liaison |

Where each kind of data lives is in docs/integration/README.md. The mapping of documents to objectives is
`do178c_dal_c.md` in the documents (docs/LIFECYCLE.md).

## A thirty minute path on example 02
Work on a copy of `examples/02_multi_interface_avionics`.

```sh
# 1. take a baseline of high-level requirements from your tool (here: a small ReqIF sample)
wireforge reqs-import avionics requirements/srs_sample.reqif --baseline SRS-B1
# 2. give the low-level requirements numbers that never change
wireforge reqs-lock avionics
# 3. generate code and tests
wireforge generate avionics -o build/gen --tests
# 4. run the tests with coverage of the generated code and of the runtime
wireforge test avionics -o build/gen --coverage-runtime --cmake-arg=-DWIREFORGE_COVERAGE_RUNTIME_MIN_LINE=0
# 5. write the documents for the baseline, with permalinks and the ReqIF export
wireforge docs avionics -o build/docs --results build/gen/avionics_demo/generated_tests/build/coverage \
  --export reqif,csv --source-url 'https://git.example.com/repo/blob/{commit}/{path}#L{line}'
```
Step 1 replaces the `requirements` section of the project with the snapshot, so remove an inline copy of the same ids
first. `--strict` makes `docs` fail when a reviewer would reject the model; the rules are in docs/LIFECYCLE.md.

## What is an id
A low-level requirement is identified by a key made of names (`SensorReading.temperature.RANGE`) and shown as
`LLR-<key>`. With `llr_ids.lock` (created by `wireforge reqs-lock`) it is shown with your numbering, for example
`SWLLR-00017`. A number is never changed or reused, also when the element is renamed (`wireforge reqs-rename-key`) or
removed. The id is the same in code comments, test properties and every document.

## Limits
- The ReqIF files WireForge writes have not been checked against the XSD of the standard or imported by a commercial
  tool yet; the pages in docs/integration say what to try first.
- There is no live connection to a requirements tool (no OSLC, no REST). Files are exchanged and kept in git.
- Tests on the target hardware and the process data around them are yours.
